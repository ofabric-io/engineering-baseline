# Baseline principles

Every change to `template/` must satisfy all four. A reviewer checks them in this order.

## 1. Generic

A core rule MUST hold for any kind of product: a CLI, a library, a SaaS, an infrastructure
platform, a data pipeline, a mobile app. Test it by naming two very different products and
asking whether the rule still makes sense for both. If it does not, it is not core.

## 2. Parameterized, not opinionated

Where a rule cannot be generic, it becomes one of:

| Form | Use when | Example |
| --- | --- | --- |
| **Bootstrap parameter** | Every project must decide it, but the answers differ | Priority order when goals conflict; name of the isolation unit |
| **Pack** | Only some kinds of project need the whole topic | `http-api`, `money`, `multi-tenant` |
| **Technology slot** | It is a stack decision | Database, language, framework |

A parameter MUST have a recommended default **and** the trade-off in one line, so the bootstrap
can offer it. A parameter with no default is an unfinished rule.

## 3. Tool-neutral

- Canonical content lives in `AGENTS.md`, `docs/`, `.agents/` and `scripts/`.
- Tool-specific files (`CLAUDE.md`, `.claude/`, `GEMINI.md`, `.github/copilot-instructions.md`,
  `.cursor/`) are **pointers**, generated by `scripts/sync-adapters.mjs`, and
  `scripts/check-adapters` fails if one holds more.
- Skills reference each other by **file path**, never by a tool's slash command.
- Questions are asked as numbered Markdown text, never through a tool-specific picker.
- The enforcement gate is git hooks plus CI. A tool's own hooks are optional early warnings that
  call the same scripts.
- The acceptance test: a human with no AI tool can bootstrap and work in a generated project.

## 4. Enforced

A rule with no enforcement mechanism is a wish. Every rule appears in its document's
`## Enforcement` table — automated (`✅`), partial (`◐`), scheduled (`⬜`), or deliberately
review-only (`❌`).

## Packs depend on the core, never the reverse

A core document MUST NOT link into a pack, so a project without that pack has no broken links.
A pack MAY amend a core rule; it says so explicitly in its `PACK.md` under `amends:`.

## New packs are grown, then promoted

A pack is not written for a hypothetical project. It starts as `docs/packs-local/<name>/`
inside a real project, is ratified there, and is promoted into the baseline with the
`promote-pack` skill once proven. See `maintainers/pack-authoring.md`.
