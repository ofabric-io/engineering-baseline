# Idempotency, Versioning & Deprecation

## Purpose

Safe retries of state-changing requests, how API versions are named and changed, and how versions are retired. The general idempotency mechanism is in `08-reliability/concurrency-and-idempotency.md`; this document is its HTTP expression.

## Parameters

| Parameter | Answer | Default | Trade-off |
| --- | --- | --- | --- |
| `idempotency_key_required_for` | [[idempotency_key_required_for]] | every state-changing request that is not idempotent by its method | Requiring it everywhere is uniform but burdens trivial operations; requiring it nowhere pushes duplicate handling onto every client |
| `idempotency_scope` | [[idempotency_scope]] | caller identity + endpoint + key | A wider scope makes accidental collisions possible; a narrower one lets one caller's key block another's |
| `idempotency_retention` | [[idempotency_retention]] | 24 hours | Longer retention costs storage; a replay after expiry re-executes, so it must exceed any client's retry window |
| `versioning_scheme` | [[versioning_scheme]] | major version in the URL path (`/v1/...`) | Header or media-type versioning keeps URLs stable but is invisible in logs, caches and bug reports |
| `unversioned_paths` | [[unversioned_paths]] | operational endpoints only (health, readiness), consumed by infrastructure | Every exemption is a route no compatibility check covers |
| `deprecation_notice_period` | [[deprecation_notice_period]] | 6 months between the `Deprecation` announcement and the `Sunset` date | Shorter suits first-party-only APIs; public APIs need longer |

## Rules

### Idempotency

- **R1.** A request in the set `idempotency_key_required_for` MUST carry an `Idempotency-Key` header; without one it MUST be rejected with the status and `code` the error catalog assigns (`responses-and-errors.md` R16).
- **R2.** The header MUST follow the IETF HTTP API idempotency-key draft (`draft-ietf-httpapi-idempotency-key-header`). It is a draft, not an RFC: the project MUST record it as such in `05-protocols/rfc-profile.md` and re-check it when it advances.
- **R3.** The key MUST be generated by the client and MUST be unique per intended operation. The server MUST NOT derive it from the payload: two distinct operations with identical payloads are not the same request.
- **R4.** The idempotency record MUST be scoped by `idempotency_scope`; the same key in another scope is an unrelated operation.
- **R5.** The idempotency record MUST be written atomically with the effect it guards (`08-reliability/concurrency-and-idempotency.md`), so a rolled-back effect leaves no record.
- **R6.** A replay with the same key and the same payload MUST return the stored original response with its original status, plus `Idempotency-Replayed: true`, and MUST NOT re-execute.
- **R7.** A replay with the same key and a different payload MUST fail with `409` and a distinct `code`; the server MUST NOT act on either version.
- **R8.** A request arriving while the original is still in flight MUST fail with `409` and a distinct `code`; the server MUST NOT wait on it or run a second copy.
- **R9.** Idempotency records MUST be retained for `idempotency_retention`, and that period MUST be stated in the API documentation.

### Versioning

- **R10.** The version MUST be expressed as `versioning_scheme` says, and MUST be declared per route group, never inferred from a global default that lets an unversioned route slip through.
- **R11.** Only the routes in `unversioned_paths` MAY be unversioned; each exemption MUST be a single, greppable allowlist entry.
- **R12.** The following are breaking changes and MUST ship as a new version: removing or renaming a field; changing a field's type or format; adding a required request field; tightening validation; adding a value to a closed set a client may switch on; changing an error `code`, or the status a condition maps to.
- **R13.** The following are not breaking and MAY ship in place: adding an optional request field, adding a response field, adding an endpoint, adding an error `code` for a genuinely new condition.
- **R14.** The API documentation MUST state that clients ignore unknown response fields; R13 depends on it.

### Deprecation

- **R15.** A deprecated endpoint or version MUST return the `Deprecation` header (RFC 9745) and the `Sunset` header (RFC 8594), and a `Link` with `rel="deprecation"` pointing at the migration guide.
- **R16.** The interval between the `Deprecation` announcement and the `Sunset` date MUST be at least `deprecation_notice_period`.
- **R17.** A version MUST NOT be removed while it still receives traffic; per-version usage telemetry decides (`07-observability/metrics-and-tracing.md`), not assumption.
- **R18.** After sunset, a removed version MUST answer `410 Gone` with a `code` naming the replacement, not `404`.

## Enforcement

| Rule | Mechanism | Status |
| --- | --- | --- |
| R1, R3, R4 | Idempotency middleware; contract test that a request without the header is rejected | ⬜ scheduled |
| R2 | Listed in `05-protocols/rfc-profile.md`; re-checked at each review of that document | ❌ review-only |
| R5 | Integration test: a rolled-back effect leaves no idempotency record | ⬜ scheduled |
| R6–R8 | Integration tests for the three replay cases | ⬜ scheduled |
| R9 | Retention job; window published in the API documentation | ⬜ scheduled |
| R10, R11 | Start-up route audit failing a route without a version unless allowlisted | ⬜ scheduled |
| R12, R13 | API-description diff against the main branch, failing on breaking changes without a new version (tool chosen in `13-technology/`) | ⬜ scheduled |
| R14 | API documentation review; the reference client ignores unknown fields | ❌ review-only |
| R15, R16 | Deprecation middleware sets both headers from route metadata; metadata review | ⬜ scheduled |
| R17 | Per-version request metric reviewed before removal | ⬜ scheduled |
| R18 | Contract test for the `410` handler | ⬜ scheduled |

## AI guardrails

- State-changing requests in the required set carry `Idempotency-Key`; never derive it from the payload.
- The idempotency record is written atomically with the effect.
- Same key and payload: return the stored response. Same key, different payload: `409`. In flight: `409`.
- Every route is versioned per `versioning_scheme`, except the allowlisted operational ones.
- Removing, renaming or retyping a field, a new required field, tighter validation, or a new value in a closed set is breaking: new version.
- Deprecate with `Deprecation`, `Sunset` and a `rel="deprecation"` link, at least `deprecation_notice_period` apart. After sunset: `410`.
