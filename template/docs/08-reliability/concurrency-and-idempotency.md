# Concurrency, Locking & Idempotency

## Purpose

How concurrent writes are controlled, how any operation with an external side effect is made safe to retry, and how background work behaves under at-least-once execution. This document owns the idempotency protocol (R7 to R16) and `idempotency_retention`. The rules are transport-neutral; a transport document adds only its wire expression and does not define a retention of its own.

## Parameters

| Parameter | Answer | Default | Trade-off |
| --- | --- | --- | --- |
| `default_concurrency_control` | [[default_concurrency_control]] | optimistic (version check on write) | pessimistic locks only where named |
| `idempotency_required_for` | [[idempotency_required_for]] | every operation with an external side effect, listed by name | exactly-once does not exist across a network |
| `idempotency_retention` | [[idempotency_retention]] | 24 hours | longer covers slower retry windows and stores more; a replay after expiry re-executes |
| `dedupe_window` | [[dedupe_window]] | 7 days for messages received from external parties | longer catches late redelivery and stores more |
| `lock_timeout` | [[lock_timeout]] | 3 seconds | longer tolerates contention and stalls pools |

## Rules

### Concurrent writes

- **R1.** Concurrent writes MUST be controlled by `default_concurrency_control` unless an operation is named as an exception.
- **R2.** Pessimistic locking MUST be used only where a read-modify-write must serialise and a retry is unacceptable, and each such operation MUST be named in this document.
- **R3.** Locks MUST be taken in a consistent order across resources and held for the shortest possible span.
- **R4.** A network call MUST NOT be made while holding a lock.
- **R5.** A write conflict MUST surface as a typed error. It MAY be retried automatically at most once, and only for a read-modify-write with no external side effect.
- **R6.** Waiting for a lock MUST be bounded by `lock_timeout`.

### Idempotency

- **R7.** Every operation in `idempotency_required_for` MUST accept an idempotency key supplied by the caller.
- **R8.** The key MUST be generated by the caller and MUST NOT be derived by the receiver from the payload.
- **R9.** A key's scope MUST be the caller, the operation and the key together; the same key for a different operation or caller is unrelated.
- **R10.** The idempotency record MUST be written atomically with the effect it guards, in the same transaction or by an equivalent mechanism.
- **R11.** A replay with the same key and the same payload MUST return the original result and MUST NOT execute the effect again.
- **R12.** A replay with the same key and a different payload MUST be rejected as a conflict and MUST NOT act on either version.
- **R13.** A request that arrives while the original with the same key is still in flight MUST be rejected as in progress; it MUST NOT wait and MUST NOT execute.
- **R14.** Idempotency records MUST be kept for `idempotency_retention`, and that retention MUST be documented to callers.
- **R15.** A message received from an external party MUST be deduplicated on the sender's own identifier within `dedupe_window`.
- **R16.** A duplicate or already-processed message MUST be acknowledged as success.

### Background work

- **R17.** Every job and message handler MUST be idempotent and MUST be written on the assumption it will run twice.
- **R18.** A scheduled job MUST run as a single instance, coordinated by leader election or a lock. _(applies to: service, daemon, batch)_
- **R19.** A distributed lock MAY be used to avoid duplicated work but MUST NOT be relied on for correctness; correctness MUST come from a unique constraint, a version check or a transactional lock.
- **R20.** A job that has exhausted its retries MUST be moved to a dead-letter destination with its context and MUST NOT be silently dropped (`08-reliability/timeouts-retries.md` R14).

### Ownership

- **R21.** A document that expresses idempotency for a transport MUST cite R7 to R14 here and MUST NOT restate or change their semantics or define its own retention parameter.

## AI guardrails

- Any operation with an external side effect takes a caller-supplied idempotency key.
- Write the idempotency record in the same transaction as the effect.
- Same key and same payload returns the original result. Same key and different payload is a conflict.
- Write every job as if it runs twice.
- Never make a network call while holding a lock.
- Never rely on a distributed lock for correctness.
